# Invariants

The rules this codebase will not bend, why each exists, and the automated check that
enforces it. **If you are an AI session with no prior context, read this file second, right
after `CLAUDE.md`.**

Every invariant here is machine-enforced. None of them rely on you remembering. If you
violate one, the pipeline goes red with a message naming the invariant — that is the
design, and it is verified by `make proof`, which plants a deliberate violation of each
rule and asserts it fires.

Two things follow from that:

- **You do not need to be careful, you need to be correct.** Write the code, run
  `make check`, and let the tools tell you what you got wrong.
- **A rule you cannot satisfy is a bug in the rule.** `make proof` also runs a *positive*
  control — a conforming slice asserted to produce zero errors. If correct code fails a
  check, fix the check, do not weaken it globally.

## Layering and structure

### INV-01 — Dependencies point one way only

`Api` → `Application` → `Domain`. `Infrastructure` → `Domain` and `Application` ports.
`Domain` depends on nothing outside itself.

**Why:** the Domain is the only part of this system that is worth keeping when the
framework changes. The moment it imports Doctrine or Symfony, it stops being portable and
starts being untestable without a container.

**Enforced by:** `backend/deptrac.yaml` · `make arch`
**Failure looks like:** `App\X\Domain\Y must not depend on App\X\Application\Z` with the
file and line.

### INV-02 — Contexts talk through facades, never internals

A bounded context may use another context only via that context's
`src/<Context>/Application/<Context>Facade.php`. `src/Api` is exempt — controllers are the
HTTP composition root.

**Why:** four contexts that reach into each other's services are one module with four
directory names. The facade is a deliberate, greppable seam: you can see every cross-context
call by listing facade usages.

**Enforced by:** `backend/deptrac-context.yaml` · `make arch`
**Failure looks like:** `App\Acl\...\X must not depend on App\Account\...\Y`.
**Adding a cross-context edge requires an ADR** — the pre-commit hook reminds you, `docs.yml`
enforces it.

### INV-03 — A new context must be registered before it means anything

Every directory under `src/` that owns a `Domain/` must appear in `deptrac-context.yaml`
(as a layer *and* a facade layer) and in `config/packages/doctrine.yaml`.

**Why:** this is the failure none of the other tools can see. Add `src/Billing/`, forget to
register it, and deptrac, PHPStan and Doctrine all report success while enforcing nothing at
all on the new code. A silently unenforced context is worse than no enforcement, because the
green pipeline says otherwise.

**Enforced by:** `tests/Architecture/EnforcementCoverageTest.php` · `make arch`
**Failure looks like:** `Context "Billing" exists under src/ but has no layer in
deptrac-context.yaml`.

### INV-04 — Domain classes are not services

Entities, value objects, enums and repository interfaces are excluded from the service
container.

**Why:** if entities are services, an entity can be autowired into a service constructor.
That produces a single shared instance of something that is supposed to be per-row, and the
bug it causes appears only under concurrency.

**Enforced by:** the `exclude` list in `backend/config/services.yaml` · `make lint`
(`lint:container`).

## The Api layer

### INV-05 — Entities are never serialized directly

Every response body is an explicit response view class under `src/Api/<Context>/Response/`.

**Why:** serializing an entity means the API contract is "whatever columns the table has
today". Adding a column then silently starts publishing it — that is how password hashes and
internal flags leak. An explicit view makes every published field a decision someone made.

**Enforced by:** code review plus the response-view shape generated by `make:api-endpoint`;
the IDOR and response-shape functional tests assert the actual bodies.

### INV-06 — Transactions are owned by Application services

`$this->transaction->wrap(...)` lives in the Application layer. Never in a controller, never
in a repository.

**Why:** a transaction is a business boundary — "these things happen together or not at
all". Controllers do not know what belongs together, and repositories only see one entity.

**Enforced by:** deptrac (controllers cannot reach Doctrine at all) and review.

### INV-07 — Controllers contain no business logic

One `final` class per endpoint, one `__invoke()`, no persistence, at least one Application
service injected, cyclomatic complexity ≤ 3, ≤ 60 lines.

**Why:** logic behind an HTTP boundary can only be tested by making requests. It also tends
to grow a second copy of an authorization decision that the ACL already owns.

**Enforced by:** `NoDoctrineInControllerRule`, `ControllerMustDelegateToServiceRule`,
phpat's `ApiShapeRules`, `phpmd-api.xml` · `make stan` and `make arch`
**Failure looks like:** `Controller X imports Doctrine\ORM\EntityManagerInterface. The Api
layer must not touch persistence: move the query into an Application service…`

### INV-08 — Application and Domain know nothing about HTTP

`Symfony\Component\HttpFoundation\*`, `HttpKernel\*` and `Security\Http\*` are forbidden
imports below the Api layer.

**Why:** a service that reads the Request cannot be called from a console command, a test or
another service without faking a web request — and it starts returning status codes, which
routes around the single error contract (ADR-0007).

**Enforced by:** `NoHttpInApplicationLayerRule` · `make stan`

### INV-11 — Every endpoint declares its permission

Every class in `src/Api` with an `__invoke()` carries `#[IsGranted(...)]`. Genuinely public
endpoints use `#[IsGranted('PUBLIC_ACCESS')]`.

**Why:** the dangerous case is not a *wrong* permission, it is a *missing* one. An endpoint
with no attribute is silently public, looks correct in review, and surfaces when someone
reads a resource they should not. Requiring the attribute turns an omission into a build
failure. `PUBLIC_ACCESS` exists so that "this is public" is a visible decision rather than an
absence.

**Enforced by:** `ControllerMustHaveIsGrantedRule` · `make stan`, plus a functional test that
walks the real router — the rule can only see code it is pointed at; the two together leave
no gap.

### INV-17 — Domain exceptions only; HTTP mapping happens once

Services throw domain exceptions. `ProblemJsonExceptionListener` is the only place that maps
an exception to a status code.

**Why:** one error contract (RFC 9457) that clients can rely on, and one place to change it.

**Enforced by:** INV-08 (no `HttpException` below Api) plus the problem+json shape test.

## The Application layer

### INV-09 — Services are `final readonly`, constructor injection only

**Why:** `final` because a subclass that overrides one method turns a single-topic service
into two behaviours sharing one name, and the parent's tests no longer prove anything about
the child. `readonly` because mutable state on a service shared across a request is the
classic bug that only appears under load.

**Enforced by:** `ServiceMustBeFinalReadonlyRule`, `ergebnis.final` · `make stan`

### INV-10 — One semantic topic per service, stated in one sentence

Every Application service carries a `@responsibility` docblock: one sentence, no
conjunction. A PDF service does nothing about string normalization.

**Why:** two things follow from it. `docs/SERVICES.md` is generated from these sentences, so
a contributor with no context can find the service that already owns a topic instead of
writing a second one. And "one topic" stops being a matter of taste — if the sentence needs
an "and", it is two classes.

**Enforced by:** `ServiceMustDeclareResponsibilityRule` (missing/empty) and the
`bentley.serviceHasTwoTopics` identifier (conjunction) · `make stan`
**Failure looks like:** `Application service X describes itself as "Renders PDF invoices and
normalizes customer address strings." A responsibility containing "and" is two topics, not
one — split this into two services.`

### INV-12 — Interfaces only at real port boundaries

Introduce an interface when there is a second implementation or a genuine port
(a mailer, a clock, an HTTP egress). **Do not** generate an interface per service.

**Why:** an interface with exactly one implementer adds a file, a layer of indirection and a
navigation step, and buys nothing. This is stated explicitly because code generators produce
them by reflex.

**Enforced by:** review. Deliberately not automated — the judgement is the point.

## Security and data

### INV-13 — Permissions are never carried in the JWT

The access token carries `sub`, `jti`, `roles` and `perm_v`. The permission set is resolved
server-side on every request.

**Why:** a permission list inside a signed token stays valid until the token expires.
Revoking access would mean waiting out the TTL. `perm_v` (the user's `acl_version`) lets a
grant change take effect on the very next request, with no re-login.

**Enforced by:** ADR-0011 and the E2E test that grants a permission and asserts the affected
user's access changes without logging out.

### INV-14 — UUIDv7 primary keys, generated by the application

**Why:** v7 is time-ordered, so it indexes like a sequential key without leaking a row count
the way an auto-increment id does. Application-generated means an entity has an identity
before it is flushed.

**Enforced by:** ADR-0013 and the `uuid` Doctrine type registered in
`config/packages/doctrine.yaml`.

### INV-18 — The audit log is append-only

`security_event` rows are inserted, never updated or deleted. The application's database
role holds INSERT only on that table.

**Why:** an audit log that the application can rewrite is not evidence of anything. The
grant is what makes it true; application-level discipline is not enough.

**Enforced by:** the migration that issues the grants, and an integration test asserting an
UPDATE is rejected.

## Frontend

### INV-16 — `v-can` and `usePermission()` hide UI, they do not authorize

**Why:** every check in the SPA is advisory. The browser is not a trust boundary — a hidden
button is still a reachable endpoint. The server decides, always.

**Enforced by:** the IDOR functional suite, which calls endpoints directly with the wrong
user and asserts 403/404 regardless of what the UI would have shown.

## Documentation

### INV-15 — Generated inventories are committed and checked

`docs/SERVICES.md`, `docs/ENDPOINTS.md`, `docs/PERMISSIONS.md` and `docs/adr/README.md` are
generated by `bin/console app:docs:generate` and committed.

**Why:** these files are how a context-free session orients itself. If they can drift, they
become misleading, which is worse than absent.

**Enforced by:** `make docs` regenerates and fails on any diff; `.github/workflows/docs.yml`
runs the same check on every PR.
